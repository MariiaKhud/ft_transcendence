# Internationalization (i18n)

Full UI translation for English, Dutch, and Ukrainian — a footer-to-database feature covering static UI text, form validation, backend API errors, and account-level persistence. This document covers *why* it's built the way it is, not just what exists. See also a brief summary in the [Internationalization section in the root README](README.md#internationalization-i18n-minor-module-implemented).

## Overview

- **Languages:** English (`en`, default/fallback), Dutch (`nl`), Ukrainian (`uk`)
- **Coverage:** Dutch and Ukrainian are at full parity with English across all 27 namespaces — enforced by `frontend/scripts/i18n.test.mjs`, so a key added to English without a matching nl/uk translation fails the suite immediately
- **Switcher:** a compact NL/EN/UA button group in the navbar (`frontend/src/components/LanguageSwitcher.tsx`), visible on every page
- **Persistence:** three-tier resolution — account preference (if logged in) → `localStorage` → browser language → English
- **Backend integration:** API errors carry a stable machine-readable `code` (87 of them) that the frontend translates, instead of showing raw English error text

## Design Decisions

These are the choices that would otherwise need re-deriving from the diff — the reasoning, not just the result.

### `react-i18next` + `i18next-browser-languagedetector`
The standard pairing for React: hooks-based (`useTranslation`), first-class plural support via `Intl.PluralRules` (needed for Ukrainian — see below), and the detector plugin handles browser-locale sniffing and `localStorage` caching without hand-rolled logic.

### Three-tier language resolution, not just `localStorage`
A guest's language choice only needs to survive a refresh (`localStorage` is enough). A logged-in user's choice should survive a *device change* — so it's also saved to `User.preferredLanguage` in the database. On login and on session restore, `applyPreferredLanguage()` (`frontend/src/lib/i18n.ts`) switches to the account's saved language *only if* it's set and differs from what's already active — guests and accounts with no saved preference are left alone, so browser detection still works for them. This is why the field is nullable rather than defaulting to `'en'`: `null` means "no opinion, keep detecting."

### Backend errors carry a `code`, not just English text
Client-side form validation was translatable from the start, but every business-rule error from the API ("email already taken", "friend request already pending", "you can't like your own article") was still raw English coming back in the `error` field. Rather than duplicate every validation rule into the frontend (fragile — two sources of truth that can drift), the backend's `AppError` class (`backend/src/middleware/error.middleware.ts`) takes a `(statusCode, code, message)` triple. `code` is a stable snake_case identifier (`backend/src/lib/error-codes.ts`); `message` stays as-is for logs and as a safe fallback. The frontend's `translateApiError()` (`frontend/src/lib/api-errors.ts`) looks up `api.errors.<code>`, and falls back to the raw English message if a code has no translation — so an unmapped edge case degrades to English instead of crashing.

This was deliberately **additive**, not a replacement: the `error` field never changed, so nothing that read it directly broke. `code` is new and optional in the API response shape (`shared/types/api.ts`).

### Ukrainian gets real CLDR plurals, not `_one`/`_other` stretched to fit
English has two plural forms; Ukrainian grammatically has four (`one`, `few`, `many`, `other` — e.g. "1 коментар", "2 коментарі", "5 коментарів"). i18next resolves the correct suffix automatically via `Intl.PluralRules` once all four keys exist (`profile.likes_one` / `_few` / `_many` / `_other`, etc.) — getting this wrong doesn't error, it just silently reads ungrammatically, so it's covered by a dedicated test rather than left to manual review.

### Legal pages are structured data, not one long string per language
`PrivacyPolicy.tsx` and `TermsOfService.tsx` read their content from nested objects/arrays in the translation JSON (headings, paragraph arrays, bullet lists — some with `{label, text}` pairs for bold lead-ins like "**Service Providers:** ..."), rendered by the same JSX structure in every language. This keeps the *document structure* (which section has a bullet list, which item is bold) identical across languages by construction, while the prose itself is fully swappable — no risk of the Dutch version silently missing a section because someone forgot to update a hardcoded `<ul>`.

### Language names shown as endonyms, never translated
The switcher shows "Nederlands" and "Українська," not translated words for "Dutch"/"Ukrainian" — every language switcher on the web works this way, and it solves the bootstrapping problem: a Ukrainian speaker looking at an English UI can still find "Українська" without being able to read English.

### Category labels: translated lookup with an algorithmic fallback
`formatCategoryLabel()` (`frontend/src/lib/article-display.ts`) looks up `common.categories.<CATEGORY>` and falls back to a naive title-case of the raw enum value if no translation exists. This means a new `Category` enum value added to the Prisma schema without a matching translation degrades to readable English instead of showing a raw key or breaking.

### What's deliberately *not* translated
User-generated content (article titles/bodies, comments, display names) and the platform's brand name ("Codamium") are left as-is everywhere — only application UI chrome is translated. Translating user data would be actively wrong (it's not the app's text to translate), and translating a brand name is not a convention any real product follows.

### Locale-aware date and number formatting, not just translated strings
`Date#toLocaleDateString()` / `toLocaleString()` / `Number#toLocaleString()` silently fall back to the *browser's* locale when called with no explicit locale argument — so a user who switched the in-app language without their OS/browser matching still saw dates and numbers formatted in the browser's language, even though every string around them was correctly translated. This surfaced during a later coverage audit (the key-parity test suite can only catch strings that already became translation keys, not native `Intl` calls that never went through `t()`). `frontend/src/lib/date-format.ts` exports `formatLocalizedDate()` / `formatLocalizedDateTime()`, which pass `i18n.language` explicitly; every date display in the app (article/comment timestamps, admin "created"/"removed at" columns, the profile join date, the notification list's >7-day fallback) goes through one of these instead of a bare `toLocaleDateString()`/`toLocaleString()`. The same fix applies to `XPBar`'s XP total (`Number#toLocaleString(i18n.language)`) and, in `frontend/src/lib/utils.ts`, to the Friends page's "last seen" relative time (`formatLastSeen()`, which now resolves through the same `notification.time.*` translation keys `formatNotificationTime()` already used, rather than returning hardcoded `'5m ago'`-style strings) and chat message timestamps (`formatMessageTime()`).

## Architecture

```
frontend/src/lib/i18n.ts                     i18next config: resources, fallback, detection order
frontend/src/lib/api-errors.ts                translateApiError(): code → translated message, with fallback
frontend/src/lib/article-display.ts           formatCategoryLabel(): category → translated label
frontend/src/lib/date-format.ts               formatLocalizedDate()/formatLocalizedDateTime(): locale-aware date formatting
frontend/src/lib/utils.ts                     formatLastSeen()/formatMessageTime(): locale-aware relative time / clock format
frontend/src/locales/{en,nl,uk}/translation.json   the actual content — one file per language, identical key shape
frontend/src/components/LanguageSwitcher.tsx  the nav UI; calls i18n.changeLanguage() + syncs to the account
frontend/src/hooks/useAuth.ts                 applies preferredLanguage on login and session restore
frontend/src/main.tsx                         <I18nextProvider> wraps <RouterProvider>

backend/src/lib/error-codes.ts                the ErrorCode registry (87 stable codes)
backend/src/middleware/error.middleware.ts    AppError(statusCode, code, message) + errorHandler
backend/prisma/schema.prisma                  User.preferredLanguage String? @map("preferred_language")
backend/src/routes/users.route-helpers.ts     validates preferredLanguage on PATCH /api/users/me

frontend/scripts/i18n.test.mjs                33-test regression suite (see Automated Testing)
```

**Request flow for an API error, end to end:** a route/service throws `new AppError(400, ErrorCode.EMAIL_TAKEN, 'Email already taken')` → `errorHandler` responds `{ success: false, code: 'email_already_taken', error: 'Email already taken' }` → the frontend catch site calls `translateApiError(err, fallbackMessage)` → if the active language has `api.errors.email_already_taken`, that's shown; otherwise the raw English `error` text is.

## Translation Key Conventions

- Namespaced by page or component: `login.*`, `article.*`, `editProfile.*`, `admin.*`, `api.errors.*`, etc. — 27 top-level namespaces currently.
- Plurals via i18next suffixes: `_one`, `_other` (all languages), plus `_few`/`_many` where Ukrainian needs them.
- Interpolation via `{{variable}}` (e.g. `"Page {{page}} of {{totalPages}}"`), passed as the second argument to `t()`.
- Shared, generic strings (Cancel, Save, Retry, category names, pagination labels) live under `common.*` rather than being duplicated per page.

## Adding a New Language

1. Add the language code to `supportedLanguages` in `frontend/src/lib/i18n.ts` and register its resource bundle in the same file's `.init({ resources: {...} })` call.
2. Create `frontend/src/locales/<code>/translation.json` — easiest starting point is copying `en/translation.json` and translating every leaf value (arrays and nested objects keep their structure; only string values change).
3. Add the language code to `LANGUAGE_ORDER`, `LANGUAGE_CODES`, and `LANGUAGE_NAMES` in `frontend/src/components/LanguageSwitcher.tsx`.
4. Add the language code to `SUPPORTED_LANGUAGES` in `backend/src/routes/users.route-helpers.ts` (this is what validates `PATCH /api/users/me`'s `preferredLanguage` field — keep it in sync with the frontend's `supportedLanguages`).
5. Run `make test-i18n` — it will fail loudly listing every missing/extra key until the new bundle has full parity with English, including plural forms if the language's plural rules differ from English's.

## Manual Testing

### Switcher and immediate UI update
1. Open the app, click through NL / EN / UA in the navbar switcher.
2. Confirm all visible text updates immediately — no page reload — across the home feed, login/register forms, search, and the Privacy Policy / Terms of Service pages.

### Persistence
3. Switch language, refresh the page. Confirm it's still applied (this part works for guests too, via `localStorage`).

### Account-level sync (the part that only applies once logged in)
4. Log in (in the browser), switch language.
5. Open dev tools → Application → Local Storage → delete the `i18nextLng` key (simulates a different browser/device that has no local record of your choice).
6. Refresh, or log out and back in. Confirm the UI comes back up in the language from step 4 — this is `preferredLanguage` being read off the account, not `localStorage`.
7. Optionally confirm the raw value via the API. A browser login doesn't give you a cookie jar `curl` can reuse, so log in via `curl` too, saving cookies to a jar — same account, separate session:
   ```bash
   curl -k -s -c /tmp/i18n.cookies -X POST https://localhost:8443/api/auth/login \
     -H "Content-Type: application/json" \
     -d '{"email":"<your-test-email>","password":"<your-test-password>"}' > /dev/null

   curl -k -s -b /tmp/i18n.cookies https://localhost:8443/api/auth/me
   ```
   Look for `"preferredLanguage": "nl"` (or `"uk"`) in the response.

### Backend error translation
8. In Dutch or Ukrainian, trigger a server-side validation error the client doesn't already catch — e.g. register with a username that's already taken. Confirm the error message is translated, not English.
9. Confirm an invalid language value is rejected with a translated-capable error code. Reuses the cookie jar from step 7 — log in first (as above) if you skipped it. `PATCH` also requires the CSRF token, which the login response set as a *readable* (non-`HttpOnly`) cookie in that same jar, so pull it out with `awk`:
   ```bash
   CSRF=$(awk '$6=="csrf_token" { print $7 }' /tmp/i18n.cookies)

   curl -k -s -X PATCH https://localhost:8443/api/users/me \
     -b /tmp/i18n.cookies -H "x-csrf-token: $CSRF" \
     -H "Content-Type: application/json" -d '{"preferredLanguage":"xx"}'
   ```
   Expect `400` and `"code":"validation_preferred_language_invalid"`. (`{"success":false,"code":"auth_required",...}` instead means the cookie jar is empty or stale — redo the login `curl` above.)

### Visual/layout check
10. Switch to Ukrainian and open the Privacy Policy page (the longest page in the app — headings, paragraphs, and bulleted lists with bold lead-ins). Confirm Cyrillic renders cleanly with no overflow or clipped text; the app loads no custom web font (see `frontend/src/index.css`), so this is exercising the OS's default UI font, not a bundled one.

## Automated Testing

```bash
make test-i18n
# or directly:
cd frontend && node --test scripts/i18n.test.mjs
```

33 tests in `frontend/scripts/i18n.test.mjs`, source-level and behavioral (no browser needed — same `node:test` pattern as `browser-compatibility.test.mjs`, no new test framework dependency). Highlights:

- **Key parity** across all three bundles, plural-suffix-aware (so Ukrainian's extra `_few`/`_many` forms don't false-positive as "extra keys"). The suite also supports a `PENDING_NAMESPACES` allowlist for namespaces still under active development by another contributor — currently empty, since every shipped namespace (including `admin.*`) has full nl/uk parity — with a second test guarding that any namespace later added to the allowlist actually exists in English, so it can't silently go stale
- **Ukrainian plural forms** — all four CLDR categories present for every count-based string
- **Bullet-list array parity** — the Privacy Policy / Terms of Service lists have the same number of items in every language
- **Cyrillic-actually-present** check — every English value with translatable prose (skipping bare codes like `"404"` and pure-interpolation strings like `"{{count}} / {{max}}"`) must have a Cyrillic counterpart in `uk`
- **Every backend `ErrorCode` has a matching `api.errors.<code>` key in all three languages, and vice versa** — reads `backend/src/lib/error-codes.ts` directly, so a new backend error code with no translation fails this test immediately instead of shipping as a silent English leak
- **A real i18next instance**, with a mocked `localStorage`, exercising `changeLanguage()` end to end and asserting the choice is actually cached — not just that the config *looks* right
- Structural checks that the provider, switcher, and error-translation helper are actually wired into the app (not just present as unused files)
- **Locale-aware date/number formatting regression guard** — every date-displaying file (article/comment cards, admin user/removed-content tables, profile, notifications) must import `formatLocalizedDate`/`formatLocalizedDateTime` from `date-format.ts` and must not contain a bare zero-arg `toLocaleDateString()`/`toLocaleString()`; the same is checked for `XPBar`'s XP total and `utils.ts`'s `formatLastSeen`/`formatMessageTime`, plus a sanity check that `en`/`nl`/`uk` don't throw as `Intl` locale tags

Beyond this suite, the feature was verified with a live, multi-page, multi-language pass driven by a real headless browser (Playwright against Chromium) against the running app — logging in through the actual UI, visiting every major page in all three languages, and asserting known English marker phrases are absent — plus visual screenshot review. That pass isn't part of the committed test suite (it needs a running app + a seeded user, so it doesn't fit a CI-style unit test), but the same approach is worth re-running after any large UI change: spin up the stack, log in through the UI once per language, and sweep page text for English leaks.

## Known Limitations

- Dutch and Ukrainian translations (including the legal pages) were produced by the development team without a native-speaker or legal review pass. Content and structure are complete and consistent across all three languages — key parity and Cyrillic-presence are enforced by tests — but wording has not been professionally reviewed.
- Category labels, error messages, and UI chrome are covered; genuinely dynamic backend-composed text embedded mid-sentence (e.g. an unknown-field-names list in a validation error, or an OAuth provider name in a "provider not enabled" message) falls back to a generic translated message rather than interpolating the dynamic part — these are edge cases unreachable through normal UI use (the frontend never sends malformed requests), not gaps in everyday translation coverage.
